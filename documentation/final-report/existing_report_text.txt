ABSTRACT

The KJIT Media Management System (MMS) is an internal, role-based web application designed to coordinate the institutional event-media lifecycle at Kristu Jayanti Institute of Technology. The platform brings event registration, media-team assignment, asset collection, reel editing, departmental approval, social-media publication tracking and academic report generation into a centralized workflow.

Faculty members register events by providing event details, category, schedule, venue, target audience, dignitary information, media coverage deadline and an event poster. The Media Team Head assigns photographers, videographers and editors. Media members upload raw and geotagged assets, while designated editors prepare and submit the final reel. The intended approval chain is Dean, HOD and Programme Coordinator. Rejection requires comments and returns the work for correction.

After final departmental approval, the Social Media Handler prepares or reviews an AI-assisted caption and manually publishes the approved content on Instagram and/or LinkedIn. The corresponding publication URLs are stored for later reference. Authorized faculty and department approvers can generate institutional reports using eight activity formats. The system also provides role-based access, event calendar views, audit logging and a storage abstraction that supports configured file storage and Google Drive integration.

The known technology stack includes Next.js, React, TypeScript, Tailwind CSS, Next.js API routes, Prisma ORM and SQLite for local development. The storage layer is designed to separate file metadata from the physical storage provider. This report documents the system requirements, workflows, diagrams, architecture, design, database concepts, testing approach and local setup procedure. Features and test outcomes that require confirmation from the final repository are explicitly identified rather than assumed.

CHAPTER 1 – INTRODUCTION

1.1 Problem Statement

Institutional events require coordinated work across faculty, media personnel, department authorities and social-media teams. Event details may be communicated through separate messages or documents; media crew assignments may be tracked independently; photographs and video assets may be stored in different locations; approval decisions may be communicated informally; and post-event reports may require repeated manual collection of the same information.

A fragmented process can lead to incomplete event information, unclear task ownership, difficulty locating original media, delays in reel review, missing approval evidence, inconsistent publication records and duplicated report preparation. It can also be difficult to determine the current state of an event or identify which role is responsible for the next action.

The project addresses the need for a centralized workflow in which event information is captured once, media responsibilities are assigned, assets are associated with the event, approvals are recorded in sequence, publication links are retained and report information can be reused. The system aims to improve traceability and reduce avoidable manual coordination.

1.2 Project Description and Module Description

The Media Management System is a private institutional web application. Users authenticate through role-specific login routes. The application presents functions according to permissions and checks authorization at API level. The lifecycle begins with faculty event registration and ends with publication tracking, report generation and audit recording.

Production hosting, institutional identity-provider integration and cloud migration are deployment decisions and must be verified separately.

CHAPTER 2 – SYSTEM STUDY

2.1 Existing System

In a conventional event-management process, event information, media assignments, original files, review feedback, publication links and reports may be maintained in separate channels. Faculty may communicate event details through forms or messages; media members may exchange files through shared drives; approvers may provide feedback through email or messaging; and report authors may re-enter event information into a prescribed template.

Such an arrangement can create duplicated records, inconsistent naming, unclear ownership, difficulty tracing revisions and additional effort when compiling reports. The description is a general analysis of common manual-process limitations and should not be interpreted as an audit of every existing institutional practice.

2.2 Proposed System

The proposed MMS provides one role-based application for the event lifecycle. Event records act as the central reference for calendar entries, assignments, media assets, approvals, publication metadata and reports. The Media Head assigns crew members; the media team captures and uploads assets; the editor submits a final reel; authorized approvers process the reel in sequence; and the Social Media Handler records the final external publication links.

The system uses a frontend/backend separation through Next.js application pages and API route handlers. Prisma provides database access. A storage service abstraction separates file handling from database records and supports configured Google Drive integration and local fallback as described in the implementation planning material.

2.4 Sequential Diagram

Figure 2.2 illustrates the interaction among human actors and technical components. The client interface sends requests to Next.js API routes. API handlers validate identity and permissions, apply business rules, persist structured records through Prisma and SQLite, and use file/Drive storage for binary assets. Responses are returned to the client so that the appropriate event, assignment, approval or publication state can be displayed.

The six visible phases are event registration, crew assignment, media ingestion and reel editing, review and approval, social-media publication, and event-report generation. During registration, the poster is stored and the event record and audit entry are created. During assignment, crew records are saved and the event status changes. During media ingestion, assets are stored and metadata is persisted. Reel submission creates the review record. Approval or rejection updates approval and event state. Publication records the platform URLs and status. Report generation retrieves event and related data and renders the selected format for export.

2.5 Activity Diagram

Figure 2.3 presents the activity flow from start to end. Faculty registration creates the event in REGISTERED state. The Media Head assigns photographer, videographer and editor roles, after which the event is marked ASSIGNED. Media coverage and Drive-folder preparation are shown as parallel branches that converge before editing. The editor prepares and submits the final reel, changing the event to REEL_SUBMITTED. The approval decision either records rejection comments and sends the reel back for correction, or advances the event to the post-approval stage.

After final approval, the workflow branches into social-media publishing and report preparation. The Social Media Handler manually publishes to Instagram and/or LinkedIn and records the URLs. Faculty selects one of the report formats, reviews automatically populated information, enters any additional participant or budget metrics and generates the report. The branches converge at final audit logging and archival.

Workflow alignment note: the supplied diagrams visibly simplify the approval actors as Dean/HOD in places. The full intended approval sequence documented for this project is Dean → HOD → Programme Coordinator. The original diagrams are retained unchanged; this textual explanation documents the complete intended sequence.

The documented menu configuration assigns user management and audit viewing to Admin; event creation and academic reports to Faculty; crew assignment to Media Head; media upload to Media Head and Media Member; and approvals to Dean, HOD and Programme Coordinator. 4.2.1 Authentication and Authorization

The project planning material describes cookie-based JWT sessions and password hashing. The authentication library is responsible for session creation and validation, while the RBAC library checks permissions. User accounts are provisioned rather than created through open public registration. Deactivated accounts should not be allowed to authenticate.

4.2.2 Audit Logging

Important operations should create audit records containing the acting user, role, action, details and timestamp, with IP address where available. Audit records support traceability for user administration, event registration, assignments, approval decisions and publication actions. Sensitive credentials, password hashes and private tokens must never be written to audit details.

4.2.3 Storage Abstraction

The StorageService abstraction isolates the application from a specific storage provider. The implementation plan describes Google Drive API v3 through a service account and a local filesystem fallback when Drive credentials are not configured. The database stores file identifiers, names, types, paths or provider references and uploader/event associations; it should not store large media binaries directly in SQLite. Actual provider selection and environment-variable handling must be confirmed from the current StorageService implementation.

CHAPTER 5 – SYSTEM DESIGN

5.1 Architectural Design

The application follows a layered web architecture. The browser renders the Next.js client interface. User actions call Next.js API routes. API handlers perform authentication, authorization, validation and workflow logic. Prisma mediates database operations against SQLite in the local configuration. The storage service writes or retrieves files through the configured provider. External services, such as Google Drive or an AI caption service, are accessed only when configured.

5.4.1 Data Integrity and Design Considerations

Use primary keys to uniquely identify records and foreign keys to maintain relationships.

Use cascading deletion only where it is safe and consistent with retention requirements; audit history should generally be retained.

Keep event core details as the primary source of truth for report generation.

Store large binary media in file/object storage and keep references/metadata in the relational database.

Validate role and workflow transitions in the backend.

Retain approval comments and revision history to support accountability.

Protect password hashes, session secrets and service-account credentials.

A formal ER diagram should be generated from the final Prisma schema. The supplied use-case, sequence and activity diagrams are not substitutes for an ER diagram.

7.1.1 Testing Approach

Testing should include unit-level validation of date and permission utilities, API integration tests for protected routes, database tests for relations and state transitions, and end-to-end tests covering the complete event lifecycle. Negative tests are essential: unauthorized users must not access restricted APIs, an approver must not skip a prior stage, invalid files must be rejected, and incomplete publication records must not be represented as published.

7.1.2 Acceptance Criteria

A user can access only the functions permitted by the assigned role.

An event can be registered with required fields and an associated poster.

The Media Head can assign event crew and the assigned users can access their tasks.

Media assets remain associated with the correct event and uploader.

Approval stages execute in the required order and rejection comments are retained.

The Social Media Handler can record separate Instagram and LinkedIn URLs for approved content.

Authorized academic users can create the applicable report formats.

Key operations are auditable and errors do not produce misleading success states.

8.10 Production Deployment Considerations

A local development server is not a production deployment. Before institutional production use, select a supported hosting environment, use a production-grade database where appropriate, configure HTTPS, secure cookies and secrets, apply least-privilege storage credentials, define media retention and backup policies, monitor application errors, and test restore procedures. If SQLite is retained, assess concurrent-write and hosting-volume constraints. A migration to PostgreSQL or managed database must be planned and tested rather than assumed to be automatic.

For media-heavy operation, object storage is generally more appropriate for large photos and videos than storing binary files in a relational database. The database should retain metadata and storage references. Google Drive may remain a staff-facing archive while a cloud object store is evaluated for application-managed media. Cloud migration is a future deployment decision, not a claim that it is already complete.
